Dumgen × Effect · reference

Glossary

Operational definitions used consistently throughout this course.

Effect

An immutable, lazy description of a computation that can succeed, fail with an expected error, and require services. An Effect is not running merely because it exists.

Runtime

The interpreter that executes an Effect. Running an Effect creates at least one fiber.

Fiber

One running execution of an Effect, managed by the Effect runtime. It has identity, status, local state, success or failure, and an interruptible lifecycle. It is a logical thread on JavaScript's event loop—not an OS thread, worker thread, or durable job.

Structured concurrency

The rule that concurrent work belongs to a lifecycle tree. Parent completion or interruption governs child fibers so work does not silently escape as an orphan.

Expected error

A failure that is part of normal operation and appears in an Effect's typed error channel, such as provider throttling. Callers can recover, retry, or transform it explicitly.

Defect

An unexpected bug or broken invariant that does not appear in the typed error channel. The runtime retains it in the fiber's Cause for reporting and diagnosis.

Service

A reusable capability required by an Effect, such as Dumgen's model adapter or provider gate. Required services appear in the Effect type's third parameter.

Layer

A recipe for constructing and supplying service implementations. A shared live Layer can build one provider client and semaphore for reuse across the application.

Semaphore

A shared gate containing a fixed number of permits. A fiber waits when it cannot acquire enough permits; Effect releases borrowed permits when guarded work finishes, fails, or is interrupted.

Retry policy

A rule that decides which typed failures deserve another attempt, how many attempts are allowed, and how long to wait between them. In Dumgen, each attempt borrows a provider permit; backoff does not.

Intake Batch

A Dumgen domain concept: one bounded, non-empty, ordered list of caller-delimited Source Sentences handled by exactly one Intake model call. Concurrency policy must not accidentally split it into one provider call per sentence.
