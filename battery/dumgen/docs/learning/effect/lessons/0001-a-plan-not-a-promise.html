Dumgen × Effect · lesson 1

A plan, not a Promise

The one distinction that makes Effect's concurrency model worth learning.

8 minutes · one retrieval check · Effect v4 RC syntax

Start from Dumgen, not FP

Dumgen currently exposes operations such as:

segment(sourceSentences: readonly string[]): Promise<SegmentationResult>

Once an async function is called, its work has started. The returned Promise lets you observe that work, but it is usually too late to redesign how the work was scheduled.

An Effect value is different: it is an immutable, lazy description of work. Constructing it starts nothing. A runtime later interprets the description.

This is not philosophical decoration. If 1,000 OpenAI requests are inert plans, a parent program can choose to run 16 at a time, cancel the children when their upload is abandoned, retry only typed transient failures, and attach one trace to the whole tree.

The type is an honest function signature

Effect.Effect<Success, Error, Requirements>

Success

The value produced. For Dumgen Intake, perhaps an ordered list of decisions.

Error

Expected failures. Provider throttling should not hide behind unknown.

Requirements

Services still needed to run, such as a model client, clock, persistence port, or concurrency policy.

Read this type:

Effect.Effect<
  readonly SegmentationDecision[],
  IntakeFailure | ProviderRateLimited,
  AiSdk
>

As: “a plan that can produce ordered segmentation decisions, can fail in these expected ways, and cannot run until an AiSdk is provided.” No monad lore required.

Enter Effect without rewriting Dumgen

The existing OpenAI SDK returns Promises. Wrap that edge with Effect.tryPromise; do not call the Promise before the wrapper's try callback runs.

import { Data, Effect } from "effect"

class ProviderError extends Data.TaggedError("ProviderError")<{
  readonly cause: unknown
}> {}

const parseResponse = (request: OpenAIRequest) =>
  Effect.tryPromise({
    try: () => client.responses.parse(request),
    catch: (cause) => new ProviderError({ cause })
  })

parseResponse(request) now returns a plan. It does not send the request. During incremental adoption, the application edge can execute it:

const response = await Effect.runPromise(parseResponse(request))

Migration rule: wrap Promises low in the dependency adapter; run Effects high at the application boundary. Calling runPromise in every leaf would throw away most of the composition benefit.

Now concurrency becomes policy

Suppose several user uploads are ready. Keep Dumgen's domain decision that one Intake Batch is one bounded, ordered provider call. Govern concurrency across batches rather than exploding every sentence into its own request:

const processUploads = (uploads: readonly Upload[]) =>
  Effect.forEach(uploads, processIntakeBatch, {
    concurrency: 16
  })

The number 16 is now visible policy. Later it can come from configuration, a shared semaphore, or adaptive provider-capacity logic without changing each workflow leaf.

Important limit: Effect makes in-process concurrency governable; it does not create provider quota, CPU parallelism, or restart durability. A “fuck ton” of requests may still require a durable queue, per-tenant fairness, idempotency, and backpressure.
