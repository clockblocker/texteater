Dumgen × Effect · lesson 5

A fiber is a running Effect

The plan is an Effect. Its live execution is a fiber.

6 minutes · one retrieval check · no low-level fiber API required

Plan versus execution

const plan = dumgen.segment(sentences) // Effect: inert plan

Effect.runPromise(plan)               // Runtime starts a fiber

Effect is the recipe. Fiber is one running instance of that recipe.

Run the same Effect twice and you get two executions—therefore two fibers—with independent outcomes and lifecycles.

Not an OS thread

JavaScript still executes ordinary code on its event-loop thread. A fiber is a logical thread managed by Effect. When one Dumgen fiber waits for OpenAI, it suspends; the runtime can advance another ready fiber.

main request fiber
├── upload A fiber  — suspended, waiting for OpenAI
├── upload B fiber  — running local projection
└── upload C fiber  — suspended, waiting for a permit

This is concurrency, not CPU parallelism. CPU-heavy parsing would still need worker threads or another process to use additional cores.

Why not just say Promise?

Identity and status

A fiber has an identity and can be running, suspended, or done.

Typed outcome

It completes with the Effect's success or error type.

Interruption

It can be cancelled while Effect runs finalizers and releases resources.

Parentage

Child work belongs to a parent lifecycle instead of silently escaping.

You usually do not create them manually

yield* Effect.forEach(
  intakeBatches,
  processIntakeBatch,
  { concurrency: 16 }
)

The runtime creates and manages concurrent child fibers for you. Start with high-level combinators; explicit forking and joining are low-level tools for cases where you need a handle on independently running work.

Dumgen payoff

If a user abandons an upload, the request's parent fiber can be interrupted. Its child provider-work fibers are interrupted too, and guarded calls release their semaphore permits. That is structured concurrency: the tree of work shares a lifecycle.

A fiber exists only inside a live runtime process. It does not survive crashes, restarts, or deploys and is not a durable queue item.
