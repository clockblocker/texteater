Dumgen × Effect · lesson 3

Bound the request flood

Turn “run many things” into visible policy without breaking Dumgen's Intake Batch.

7 minutes · one retrieval check · Effect v4 RC syntax

Concurrency is explicit

This program is sequential:

const results = yield* Effect.all(effects)

Effect's current default is one operation after another. To permit at most sixteen active children, say so:

const results = yield* Effect.all(effects, {
  concurrency: 16
})

The concurrency number belongs to the parent workload, not to each network call. That makes capacity a policy you can find, test, and change.

all versus forEach

Effect.all

You already have a fixed structure of Effect values and want one Effect containing all their results.

Effect.forEach

You have a collection of inputs and a function that constructs one Effect for each input.

// Fixed Effects
yield* Effect.all(
  [processBatch(first), processBatch(second)],
  { concurrency: 2 }
)

// Collection of batch inputs
yield* Effect.forEach(
  intakeBatches,
  processBatch,
  { concurrency: 16 }
)

Both produce one parent Effect. The caller can yield that parent inside a larger Effect.gen workflow.

The same Dumgen work, two ways

const batches = [batchA, batchB, batchC]

// Step 1: turn each Batch value into an Effect value.
const effects = batches.map(processBatch)
// effects is [Effect, Effect, Effect]

// Step 2: combine those Effect values.
const withAll = Effect.all(effects, { concurrency: 2 })

// forEach performs those two conceptual steps together.
const withForEach = Effect.forEach(
  batches,
  processBatch,
  { concurrency: 2 }
)

Effect.forEach(values, f, options) is the collection-shaped spelling of Effect.all(values.map(f), options).

Use all when the Effects are unlike each other

const [segmented, policy] = yield* Effect.all([
  dumgen.segment(sentences), // Effect<Segmentation, ...>
  loadConcurrencyPolicy     // Effect<Policy, ...>
])

You manually assembled two different Effects and want their differently typed results.

Use forEach when one recipe handles many values

const segmentations = yield* Effect.forEach(
  intakeBatches,                        // IntakeBatch[]
  (batch) => dumgen.segment(batch.items), // Batch → Effect
  { concurrency: 16 }
)

You have many values of one kind and apply the same Effect-producing function to each.

Preserve the Dumgen boundary

An Intake Batch is one bounded, ordered list handled by one model call. Do not confuse “concurrent uploads” with “one provider call per sentence.”

const processUploads = (batches: readonly IntakeBatch[]) =>
  Effect.forEach(
    batches,
    (batch) => dumgen.segment(batch.sourceSentences),
    { concurrency: 16 }
  )

Sixteen batches may be active. Each batch still crosses the provider boundary as the single call required by Dumgen's domain model.

The dangerous setting

{ concurrency: "unbounded" }

This removes the combinator's limit. It does not mean “as fast as safely possible”; it means this parent program supplies no bound. That is usually wrong for paid, rate-limited provider traffic.

Scope warning: concurrency: 16 limits children of this one combinator. If twenty user requests each start their own parent program, you could still have 320 provider calls. A shared provider-wide limit requires a shared semaphore or queue—a later lesson.

Retrieval check

What does { concurrency: 8 } guarantee?

  1. At most eight child Effects run.
  2. Exactly eight child Effects always run.
  3. Eight requests survive every process restart.
